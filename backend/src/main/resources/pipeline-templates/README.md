# Структура шаблонов пайплайнов

## Расположение и именование

```
pipeline-templates/
├── gitlab-ci/                     # → .gitlab-ci.yml
│   ├── java-maven.yml.ftl         # готов (итерация 0)
│   ├── typescript-npm.yml.ftl     # итерация 1
│   └── python-pip.yml.ftl         # итерация 1
└── jenkins/                       # → Jenkinsfile
    ├── java-maven.groovy.ftl      # готов (итерация 0)
    ├── typescript-npm.groovy.ftl  # итерация 1
    └── python-pip.groovy.ftl      # итерация 1
```

Имя шаблона: `{язык}-{сборщик}.{расширение}.ftl` (в нижнем регистре).
Генератор (`TemplatePipelineGenerator`) находит шаблон по результату анализа автоматически:
чтобы поддержать новый стек, достаточно добавить файл шаблона — код менять не нужно.
Если шаблона нет, API возвращает ошибку `UNSUPPORTED_STACK`.

## Шаблонизатор

FreeMarker. Подстановка переменных — в синтаксисе `[=имя]`, а не `${имя}`,
потому что GitLab CI (`$CI_COMMIT_SHA`) и Jenkins (`${env.BUILD_NUMBER}`)
используют похожий синтаксис, и он должен попадать в итоговый файл без изменений.
Условия и циклы — обычные теги FreeMarker: `<#if hasTests> ... </#if>`, `<#list frameworks as f>`.

## Переменные, доступные в каждом шаблоне

| Переменная        | Тип          | Пример            | Откуда              |
|-------------------|--------------|-------------------|---------------------|
| `languageVersion` | строка       | `"21"`, `"3.12"`  | анализатор          |
| `branch`          | строка       | `"main"`          | запрос или анализатор |
| `hasTests`        | логическое   | `true`            | анализатор          |
| `hasDockerfile`   | логическое   | `false`           | анализатор          |
| `frameworks`      | список строк | `["spring-boot"]` | анализатор          |

## Этапы пайплайна

Каждый шаблон строится из одинаковых этапов, часть из которых включается по условию:

1. **checkout** — получить код (всегда);
2. **setup** — установить язык нужной версии и включить кэш зависимостей (всегда);
3. **build** — собрать проект (всегда);
4. **test** — запустить тесты (если `hasTests`);
5. **docker** — собрать образ (если `hasDockerfile`);
6. **deploy** — планируется в следующих итерациях.

## План развития (итерация 1)

- Шаблоны для TypeScript/npm и Python/pip.
- Вынос общих этапов в подключаемые фрагменты (`<#include>`), чтобы не дублировать их между стеками.
- Учёт фреймворков (например, отдельный шаг для Spring Boot или React).
- Этап deploy (например, на тот же хостинг, где будет MVP).
